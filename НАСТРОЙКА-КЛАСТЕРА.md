# Полная настройка отказоустойчивого кластера Termidesk VDI 7.0

Пошаговое описание: **что делать**, **в каком порядке**, **на каких узлах**, **что вводить в панели**, **что проверить**.  
Работайте через пункт меню **[18]** (без захардкоженных параметров).

Официальная документация: https://termidesk.ru/docs/ru-termidesk-doc/v7.0/index.html

---

## A. Что вы получите в итоге

Отказоустойчивый контур:

1. Общая БД PostgreSQL (режим `DB_CLUSTER_MODE=cluster` в Termidesk).
2. Брокер RabbitMQ (очереди задач и регистрация шлюзов).
3. ≥ 2 Универсальных диспетчера (портал/API), один — **эталон**.
4. ≥ 2 Менеджера рабочих мест CeleryMan (в типе **standard** — отдельные узлы).
5. ≥ 2 шлюза Termidesk Connect (websockify).
6. Балансировщик nginx с VIP FQDN для пользователей.
7. Единый `termidesk-settings.json` и скрипты в `output/18-ha-wizard/`.

Панель **не заменяет** полноценный HA PostgreSQL (Patroni и т.п.) и интерактивный `termidesk-config` — она готовит параметры/скрипты и ведёт по порядку работ.

## C. Подготовка Windows-станции администратора

1. Скопируйте каталог `termidesk` **целиком** (файлы `.ps1`/`.psm1` должны быть UTF-8 **с BOM**).
2. Установите OpenSSH Client (`ssh`, `scp` в PATH).
3. Разрешите скрипты при необходимости:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

4. Проверьте доступ к каждому Linux-узлу:

```powershell
ssh -p 22 USER@IP "hostname; sudo -n true || sudo -v; timedatectl || date"
```

5. Запустите панель **одним из способов:**

**Интерактивный мастер:**

```powershell
cd C:\path\to\termidesk
.\Start-TermideskMenu.ps1
# → [18] → [1]
```

**Или предзаполненный JSON** (шаблон `config/ha-cluster.template.json`, гайд `ГАЙД-ШАБЛОН-JSON.html`):

```powershell
Copy-Item .\config\ha-cluster.template.json .\config\my-ha-cluster.json
# заполните __ЗАПОЛНИТЕ__ в my-ha-cluster.json
.\Start-TermideskMenu.ps1 -SettingsFile .\config\my-ha-cluster.json -GenerateHa -HaWizard -Force
```

6. Справка: меню **[H]**; настройка кластера — `НАСТРОЙКА-КЛАСТЕРА.html`; JSON — `ГАЙД-ШАБЛОН-JSON.html` / **[18]→[T]**.

## D. Подготовка Linux-узлов (до панели или шаг 1)

На **каждом** узле кластера:

1. Установить поддерживаемую ОС (Astra Linux и т.п. по матрице Termidesk 7.0).
2. Задать hostname = короткое имя; прописать FQDN в DNS или `/etc/hosts` на всех узлах.
3. Создать пользователя SSH с `sudo`.
4. Открыть firewall между ролями (см. раздел портов ниже).
5. Обеспечить доступ к репозиторию Termidesk и обновлениям ОС.

Чеклист сети:

- [ ] Клиенты → VIP:443 (и :80 при редиректе)
- [ ] LB → диспетчеры:443 (или ваш порт HTTPS)
- [ ] LB → шлюзы:websockify (часто 5099)
- [ ] Диспетчеры/Celery → PostgreSQL:5432
- [ ] Диспетчеры/Celery/шлюзы → RabbitMQ:5672
- [ ] Админ → все узлы:22
- [ ] NTP доступен со всех узлов

### E.2. Что вводить на каждом этапе мастера

Идите по экранам **без пропуска обязательных полей**.

#### 1) Тип развёртывания

- `1` — standard  
- `2` — minimal  

#### 2) Общие параметры

| Поле | Что указать |
|------|-------------|
| DNS-домен | Ваш домен инфраструктуры |
| NTP | IP или FQDN корпоративного NTP |
| Репозиторий Termidesk | URL/строка от вендора для 7.0 |
| Репозиторий Astra | При необходимости; можно пусто |

#### 3) SSH

| Поле | Что указать |
|------|-------------|
| Пользователь | Единый admin на всех узлах |
| Порт | Обычно 22 |
| Ключ | Путь к `id_rsa` / ed25519; можно пусто |

#### 4) PostgreSQL

| Поле | Что указать |
|------|-------------|
| DB_CLUSTER_MODE | `cluster` для HA (или `single` для одного сервера) |
| DBHOST / DBHOST2 / DBHOST3 | IP или FQDN узлов БД |
| DBPORT | Обычно 5432 |
| DBNAME / DBUSER / DBPASS | Учётка приложения Termidesk |
| CIDR pg_hba | Сеть, откуда ходят диспетчеры и Celery |

**Отдельно от панели:** если нужен настоящий HA БД — поднимите Patroni/репликацию **до** или **параллельно**, а в мастере укажите адреса, которые Termidesk будет перебирать до master.

#### 5) RabbitMQ

| Поле | Что указать |
|------|-------------|
| Тип | Обычно RabbitMQ (`1`) |
| Хост / порт AMQP | Узел брокера, порт 5672 |
| Management | 15672 (или свой) |
| User / password / vhost | Учётка; vhost часто `/` |

#### 6) OpenBao

- Если секреты в конфигах — ответьте **N**.
- Если OpenBao уже есть — **Y** и заполните URL, KV, AppRole, пути секретов.

#### 7) TLS балансировщика

| Режим | Когда |
|-------|-------|
| Самоподписанный (`1`) | Стенд/лаба — скрипт сам создаст cert/key **и** `dhparam.pem` на LB |
| Существующие файлы (`2`) | Production: ваш `.crt` и `.key` уже лежат (или будут лежать) **на Linux-балансировщике** |

#### Что спрашивает мастер и что отвечать

Все пути — **на Linux-узле nginx**, не на Windows-ПК администратора.

| Вопрос мастера | Что это значит | Что обычно вводить |
|----------------|----------------|--------------------|
| Путь к SSL-сертификату на балансировщике | Файл `.crt` / `.pem` сертификата VIP | `/etc/ssl/certs/portal.crt` |
| Путь к закрытому ключу SSL | Файл `.key` | `/etc/ssl/private/portal.key` |
| **Путь к dhparam.pem** | См. блок ниже | **`/etc/nginx/dhparam.pem`** |
| DNS resolver primary / secondary | DNS для `ssl_stapling` в nginx | IP ваших корпоративных DNS |

#### Вопрос «Путь к dhparam.pem» — что он от вас хочет

Мастер **не просит ваш сертификат ещё раз**.

`dhparam.pem` — отдельный служебный файл **параметров Diffie–Hellman** для nginx (директива `ssl_dhparam`). Он нужен для усиления TLS (DHE). Это **не** `.crt` и **не** `.key`.

**Что ввести в ответ на вопрос мастера:**

```text
/etc/nginx/dhparam.pem
```

#### Как сделать файл dhparam.pem

Файл создаётся **на Linux-балансировщике** (узел nginx), не на Windows.

**Способ 1 — вручную (рекомендуется сделать заранее)**

1. Подключитесь по SSH к балансировщику:

```bash
ssh USER@IP_БАЛАНСИРОВЩИКА
```

2. Создайте каталог (если нужно) и сгенерируйте файл:

```bash
sudo mkdir -p /etc/nginx
sudo openssl dhparam -out /etc/nginx/dhparam.pem 4096
```

3. Дождитесь окончания. Генерация **4096 бит** может занять **от нескольких минут до 15–20+ минут** — это нормально, не прерывайте.

4. Проверьте, что файл появился и не пустой:

```bash
ls -lh /etc/nginx/dhparam.pem
sudo head -n 2 /etc/nginx/dhparam.pem
```

Должно начинаться примерно так: `-----BEGIN DH PARAMETERS-----`

5. Права (по желанию, только root читает ключ-подобные файлы):

```bash
sudo chmod 644 /etc/nginx/dhparam.pem
```

(для `ssl_dhparam` обычно достаточно `644`; главное — файл существует и читается пользователем nginx.)

**Способ 2 — через панель**

1. В мастере **[18]** на вопрос «Путь к dhparam.pem» укажите `/etc/nginx/dhparam.pem`.
2. На шаге развёртывания nginx (**[18] → 8**) скрипт `08-nginx-lb-setup.sh` сам выполнит `openssl dhparam`, **если файла ещё нет**.
3. Учтите: шаг nginx «зависнет» на генерации на то же долгое время — это ожидаемо.

**Ускоренный вариант для стенда (слабее, только лаба):**

```bash
sudo openssl dhparam -out /etc/nginx/dhparam.pem 2048
```

Для production оставляйте **4096**.

**Если openssl нет:**

```bash
sudo apt update
sudo apt install -y openssl
```

После создания файла путь в мастере / в `termidesk-settings.json` → `cluster.tls.dhparamPath` должен совпадать с реальным путём на LB (обычно `/etc/nginx/dhparam.pem`).

#### Частая ошибка: пути Windows

Не указывайте:

```text
C:\_Scripts\SSL\certs\something.crt
```

Nginx на Astra/Linux эти пути не видит. Скопируйте сертификат и ключ на балансировщик (`scp`) в `/etc/ssl/...` и в мастере пишите уже Linux-пути.

Для self-signed дополнительно: срок (дней), размер ключа RSA, CN = FQDN VIP.

#### 8) Диспетчеры

1. Число ≥ 2.
2. `NODE_ROLES`: standard → `ADMIN,USER`; minimal → `ADMIN,USER,CELERYMAN`.
3. Для каждого: NODE_NAME, FQDN, IP. **Первый = эталон.**
4. URL портала (можно `https://эталон-FQDN`), логин/пароль admin.

#### 9) CeleryMan (только standard)

≥ 2 узла (name/fqdn/ip), порты health beat/worker (часто 8103/8104).

#### 10) Шлюзы

≥ 2 узла + порт websockify; `coordinatorUrl` вида `amqp://user@rabbit-host:5672/`, user/pass, `healthCheckPath` (часто `/api/health`).

#### 11) nginx / LB

FQDN VIP, VIP IP (необяз.), узлы LB,  
`listen` HTTP/HTTPS (пример: `0.0.0.0:80` и `0.0.0.0:443 ssl`),  
порт HTTPS диспетчеров, proxy timeout, каталоги snippets и include-пути.

#### 12) Health Check

`HEALTH_CHECK_ACCESS_KEY` (обязательно), metrics key — по желанию.

### Шаг 1. Подготовка среды (`01-prepare-environment.sh`)

**Куда:** все узлы (или хотя бы те, куда ставите пакеты Termidesk / nginx / БД / RabbitMQ).

**Что делает скрипт:**

- прописывает NTP;
- добавляет репозиторий Termidesk (и Astra, если задан);
- `apt update`.

**Что сделать вам:**

1. В **[18]** выбрать шаг **1**, подтвердить SSH на целевой IP (или выполнить вручную на каждом узле).
2. Повторить для всех узлов кластера (скрипт один — цель меняется).
3. Проверить:

```bash
timedatectl status   # или date на всех узлах — время совпадает
apt-cache policy termidesk-vdi
```

**Не переходите дальше**, пока NTP и репозиторий не работают везде.

---

### Шаг 2. PostgreSQL (`02-postgresql-setup.sh`)

**Куда:** узел БД (как минимум master / DBHOST).

**Что делает:**

- ставит `postgresql` (если ещё нет);
- создаёт БД и пользователя;
- печатает строку для `pg_hba.conf`.

**Что сделать вам:**

1. Выполнить шаг **2** на DBHOST.
2. Вручную добавить в `pg_hba.conf` доступ из CIDR приложений (как в мастере), затем `reload`.
3. Если HA БД — настроить репликацию/Patroni по вашей схеме; убедиться, что приложение видит master.
4. Проверка с диспетчерской сети:

```bash
psql -h DBHOST -p 5432 -U DBUSER -d DBNAME -c 'SELECT 1'
```

Локаль БД в скриптах ориентирована на `ru_RU.utf8` — локаль должна быть доступна в ОС.

---

### Шаг 3. RabbitMQ (`03-rabbitmq-setup.sh`)

**Куда:** узел брокера.

**Что делает:**

- ставит `rabbitmq-server`;
- кладёт конфиги из шаблонов;
- включает management plugin;
- перезапускает сервис.

**Что сделать вам:**

1. Выполнить шаг **3**.
2. Создать пользователя/vhost/права, если скрипт не создал их под ваши пароли (сверьте с официальным гайдом и вашими значениями из JSON):

```bash
sudo rabbitmqctl status
sudo rabbitmqctl list_users
# при необходимости:
# sudo rabbitmqctl add_user ...
# sudo rabbitmqctl set_permissions -p / ...
```

3. Открыть management UI `http://RABBIT:15672` (если политика ИБ позволяет) и проверить доступ.
4. С узлов диспетчера/шлюза проверить TCP 5672.

### Шаг 4. Первый диспетчер — эталон (`04-dispatcher-reference.sh`)

**Куда:** IP эталонного диспетчера (первый в списке).

Это **гайд**: часть действий интерактивна.

**Порядок работ:**

1. Открыть шаг **4** в меню — прочитать инструкцию / выполнить установку пакета.
2. На эталоне:

```bash
sudo apt install -y termidesk-vdi
cd /opt/termidesk/sbin
sudo ./termidesk-config
```

3. В `termidesk-config` указать **те же** параметры, что в `termidesk-settings.json`:
   - farm mode / роли / NODE_NAME эталона;
   - DB_CLUSTER_MODE, DBHOST…, DBNAME, DBUSER, DBPASS;
   - RabbitMQ URL / user / password / vhost;
   - secrets storage (config или OpenBao);
   - HEALTH_CHECK_ACCESS_KEY.
4. Дождаться успешного старта служб:

```bash
systemctl status termidesk-vdi
# и связанные unit'ы по документации вашей сборки
```

5. Войти в веб-портал по `https://эталон-FQDN` (или временно по IP) под admin — убедиться, что UI открывается.
6. Сохранить каталог конфигурации для копирования на другие диспетчеры:

```bash
# с эталона (пример из гайда панели)
sudo tar czf /tmp/termidesk-vdi-etc.tgz -C /etc/opt termidesk-vdi
# или scp -r /etc/opt/termidesk-vdi user@other:/home/user/
```

Сверьте сниппет: `output/18-ha-wizard/termidesk.conf.snippet`.

**Не ставьте остальные диспетчеры**, пока эталон не работает с БД и RabbitMQ.

---

### Шаг 5. Дополнительные диспетчеры (`05-dispatcher-additional.sh`)

**Куда:** каждый диспетчер кроме эталона.

**Порядок:**

1. Скопировать `/etc/opt/termidesk-vdi` с эталона на целевой узел (в home, затем в `/etc/opt/`).
2. Установить пакет `termidesk-vdi`.
3. В конфиге сменить **`NODE_NAME`** на уникальное имя этого узла (роли как у диспетчеров).
4. Параметры БД и RabbitMQ — **идентичны** эталону (не создавать новую БД).
5. Запустить службы, проверить:

```bash
systemctl status termidesk-vdi
journalctl -u termidesk-vdi -e --no-pager | tail -n 50
```

6. Повторить для всех дополнительных диспетчеров.

Оба (все) диспетчера должны видеть одну БД и один брокер.

---

### Шаг 6. CeleryMan (`06-celery-setup.sh`) — только standard

**Куда:** каждый узел CeleryMan.

**Порядок:**

1. Скопировать конфиг с эталонного диспетчера (`/etc/opt/termidesk-vdi`).
2. Выполнить скрипт шага **6** (или вручную): положить `termidesk-vdi.local`, выставить `NODE_ROLES=CELERYMAN`, установить пакет.
3. Уникальный `NODE_NAME` на каждом CeleryMan.
4. Проверить порты health (8103/8104 или ваши) и службы celery beat/worker по документации.
5. Повторить на втором (и далее) узле CeleryMan.

Для **minimal** шаг пропускается — роли Celery уже на диспетчерах.

---

### Шаг 7. Termidesk Connect — шлюзы (`07-gateway-setup.sh`)

**Куда:** каждый шлюз.

Это **гайд** по настройке Connect.

**Порядок на каждом шлюзе:**

1. Установить Termidesk Connect по официальной инструкции вашей версии.
2. Задать:
   - `coordinatorUrl`, `coordinatorUser`, `coordinatorPass` — как в мастере;
   - порт websockify;
   - `healthCheckPath`.
3. Убедиться, что шлюз зарегистрирован в RabbitMQ и отвечает на health.
4. С балансировщика проверить доступность `IP:websockify_port`.

Повторить для всех шлюзов (≥ 2).

---

### Шаг 8. Балансировщик nginx (`08-nginx-lb-setup.sh`)

**Куда:** узел(ы) LB.

**Что делает скрипт:**

- ставит nginx/openssl;
- генерирует self-signed **или** использует ваши пути сертификатов;
- пишет snippets SSL и site с upstream на диспетчеры и шлюзы;
- `nginx -t` и restart.

**Что сделать вам:**

1. Если режим «существующие файлы» — **заранее** положите cert/key (и при необходимости dhparam) по указанным путям.
2. Выполнить шаг **8**.
3. Проверить:

```bash
sudo nginx -t
systemctl status nginx
curl -kI https://VIP-FQDN/
# websockify путь зависит от конфигурации клиентов
```

4. DNS: A-запись VIP FQDN → VIP IP (или hosts на клиентах для стенда).
5. Если два LB — настройте Keepalived/внешний VIP отдельно; скрипт настраивает nginx на конкретном узле.

В `output/18-ha-wizard/nginx-site.conf` можно сверить upstream’ы: IP диспетчеров и шлюзов должны совпадать с таблицей из раздела B.

### Шаг 9. Проверка кластера (`09-healthcheck.ps1`)

**Откуда:** Windows (пункт **[18] → 9**).

Проверяет ICMP-доступность узлов из конфигурации и печатает VIP.

Дополнительно вручную:

| Проверка | Как |
|----------|-----|
| Портал через VIP | Браузер `https://VIP-FQDN` |
| Портал напрямую | `https://dispN-FQDN` |
| Службы | `systemctl status` на диспетчерах, celery, nginx, rabbit, postgres |
| Отказ одного диспетчера | Остановить один `termidesk-vdi` — VIP должен продолжать отвечать |
| Отказ одного шлюза | Аналогично для Connect |
| БД | Application всё ещё стартует при DBHOST2/3 при падении одного узла (если HA БД настроен) |

## I. Типичные стоп-факторы

| Симптом | Что проверить |
|---------|----------------|
| Кракозябры / ParserError в меню | UTF-8 BOM у `.ps1`/`.psm1` |
| Шаг SSH падает | OpenSSH, sudo, firewall 22, ключ |
| Эталон не стартует | БД (pg_hba, пароль), RabbitMQ, NTP |
| Второй диспетчер «ломает» первый | Не создавали ли вторую БД; один и тот же conf кроме NODE_NAME |
| VIP открывается, сессии нет | Шлюзы, `/websockify`, upstream nginx, RabbitMQ coordinator |
| Браузер ругает сертификат | Self-signed на стенде — норма; в бою — корпоративный cert на VIP |
| Мастер спрашивает «Путь к dhparam.pem» | Ввести `/etc/nginx/dhparam.pem`. Это **не** сертификат, а файл Diffie–Hellman для nginx. Подробно — раздел «7) TLS» выше. Нельзя `C:\...` |
| Указали пути `C:\_Scripts\SSL\...` | Неверно для nginx. Скопируйте cert/key на LB в `/etc/ssl/...` и укажите Linux-пути |
| Celery не выбирает primary | Два CeleryMan, порты health, общий брокер/БД |
